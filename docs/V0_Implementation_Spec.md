# 自主学习求解系统 Benchmark V0 实施规范

版本：0.3  
日期：2026-10-03  
面向：本地 coding agent 与项目开发者  
本轮交付：可运行的本地实验框架、测试环境、示例求解器、验收证据和可回传审阅包。

本文替代 0.2 版中关于 V0 实施范围的约定。V0 只建立通用实验骨架；具体任务的完整开发、强参考方法和自主 agent 实验进入 V1。本文规定的是待实现行为，示例命令不是已经存在的工具。

## 1 项目目标与版本边界

长期研究问题是：面对新任务，通用 agent 能否自主建立轻量求解系统，持续训练它，并学会何时依赖它，使性能、成本和延迟随适应而改善？

最终参赛系统可以同时包含代码、学习模型、搜索、持久经验、调用判断与 LLM。它是常驻的决策程序，可以不调用 LLM 而直接行动，也可以在局内或局间开发和训练模块。

### 本次只实现 V0

V0 的完成标准是：换一个游戏或一种求解方法，能够复用运行、记录、保存和评测流程。

V1 再对每个具体任务执行三个阶段：

1. 开发环境，提供 RL 与可视化交互接口，验证规则。
2. 用最多 3–5 种代表性的 RL、搜索或组合方法建立强参考策略，并测量资源成本。
3. 接入自主 agent，评估其自行建立、训练和使用模块的能力。

首个 V1 候选为微型拼板，Harmonies 留作后续任务。V0 不实现这两个游戏，不训练强 RL，不展开完整方法对照。

### 默认工程选择

- 单机、单玩家、同步运行；Python 项目，CPU 可以完成全部必需验收。
- 一个主要进程中的常驻 Solver；本地训练或开发任务可以使用同步子进程。
- 配置和结果使用 JSON，事件使用 JSONL，checkpoint 使用普通目录。
- 先完成本地运行器；Harbor、容器和远程执行以后通过适配接入。
- 提供简单的本地浏览器交互页和轨迹回放，不开发完整前端平台。
- 不提前实现分布式训练、热更新、任意进程内存快照、多人调度或多租户权限系统。

这些选择用于降低实现量。字段、类名和辅助文件可以合理调整，但必须保留本文的行为，并在 README 给出实际可执行入口。

## 2 四个模块及依赖关系

| 模块 | 职责 | 不放在这里的内容 |
| --- | --- | --- |
| `environment` | 真实规则、状态推进、玩家观测、反馈和计分，以及 RL、搜索、展示的薄适配层。 | 训练算法、LLM 调用判断。 |
| `solver` | 决策、自建模型、经验、搜索或学习逻辑；保存和恢复自身产物。 | 为适配接口而重复维护基准真引擎。 |
| `runner` | 多局调度、Context、模型调用包装、本地任务执行、基础预算和测量。 | 任务专属置信度阈值、RL 算法、自动兜底策略。 |

依赖原则：Environment 不依赖 Solver；Runner 面向公共接口，不按求解器类型写不同实验循环；UI 只呈现玩家观测和提交动作；Artifacts 记录运行事实，不反过来决定策略。

Solver 可以自行编写或学习环境模型；这属于参赛系统的产物，与基准提供的真实引擎分开。不要把“共用一套真实规则”理解为禁止 agent 自建模拟器。

## 3 V0 唯一测试环境 风险采集

### 3.1 规则

一局使用一个袋子，初始有 8 张牌：收益牌 `[1, 1, 2, 2, 3, 3]` 和 2 张失败牌。

- 初始累计收益为 0。
- `DRAW`：从剩余牌中均匀随机抽取一张，不放回。收益牌的数值加入累计收益；失败牌使本局得分为 0，并立即结束。
- `BANK`：以当前累计收益作为最终得分，立即结束。初始就 BANK 是合法的，得分为 0。
- 新局重新装袋，不保留上一局的牌或累计收益。
- 正常游戏中，抽到失败牌或执行 BANK 都是自然终止。

首版训练反馈采用：未终止时 reward 为 0；BANK 终止时 reward 等于累计收益；失败终止时 reward 为 0。因此一局 reward 总和等于真实得分。

这个环境只用于验证框架。其策略可以很简单；V0 不以超过某个分数或证明 RL 有效作为完成条件。

### 3.2 玩家观测与随机性

观测包含：累计收益、各类剩余牌数量、步数、终止标志，以及终止后的真实得分。初始牌组成公开，因此剩余数量也是玩家可知信息。未来随机抽牌结果不可见。

建议使用“剩余牌计数加随机抽样”实现，不预生成并向求解器提供未来牌序。真实环境、搜索模拟、Solver 自身随机性分别使用独立随机流；相同配置和相同种子能够重复结果。

不要让游戏引擎读取全局随机状态，也不要让搜索消耗真实环境的随机流。

## 4 Environment 契约

### 4.1 基础接口

以下是建议签名，类型可以用 dataclass 与普通字典实现：

```python
reset(seed: int) -> tuple[Observation, dict]
step(action: Action) -> StepResult
```

`StepResult` 至少包含：

| 字段 | 语义 |
| --- | --- |
| `observation` | 执行动作后的玩家可见观测。 |
| `reward` | 本次真实环境反馈；不与 Solver 自建奖励混用。 |
| `terminated` | 游戏规则导致的自然终止。 |
| `truncated` | 预算、超时或外部停止。正常引擎转移不设置它，运行适配层可以设置。 |
| `info` | 公开的动作结果、终止原因；自然终止时包含真实得分。 |

非法动作不改变状态和随机流，返回明确错误；Runner 记录一次动作请求。V0 不必支持分布式请求重试协议。终止后继续 step 应报错，不能隐式 reset。

### 4.2 三种使用方式共用一套规则

**RL 适配器**：将基础接口转换为便于训练使用的观测编码、reset 和 step 返回值。V0 只需一个薄适配器与调用示例，不要求安装 RL 算法库或实现并行训练。编码不得增加原观测中没有的信息。

**搜索适配器**：显式提供 `fork(sim_seed)` 或等价能力，复制当前游戏局面，并使用独立模拟随机流生成后续。模拟结果不能改变真实环境。引用正确模拟器的能力通过实验配置提供给参考搜索，不作为所有 Solver 的默认能力。

**交互适配器**：显示玩家观测，提供 DRAW、BANK、新局按钮，并显示得分。动作仍由同一个环境引擎处理。回放模式只读取记录，不重新随机生成结果。

RL 采样和搜索 rollout 可以直接调用本地引擎。Headless 运行不启动 UI；模拟步骤不经过模型 API，不逐步生成真实交互日志。模拟次数可以汇总记录。

### 4.3 搜索复制的明确含义

V0 风险采集中的剩余牌数量完全可知，搜索可从它们抽样。`fork(sim_seed)` 不复制真实环境未来的 RNG 状态给搜索，而是建立一个新随机流。

将来遇到隐藏手牌等任务，搜索应如何建立 belief 或抽样隐藏状态，需要由该任务再定义。V0 不把“复制全部隐状态”承诺为通用参赛接口。

验收时须证明：对某个真实局面执行大量搜索模拟后，真实环境在同样动作序列下的后续结果不变。

## 5 Solver 与 Context 契约

### 5.1 常驻 Solver 生命周期

建议提供以下钩子，不需要使用的钩子可以是空实现：

```python
start_task(context) -> None
start_episode(observation, context) -> None
decide(observation, context) -> Action
on_transition(transition, context) -> None
end_episode(result, context) -> None
save(directory) -> None
load(directory) -> None
```

`transition` 包含前后观测、动作及执行反馈；`result` 包含该局结束原因、真实得分或失败状态。它们不携带环境内部对象。

同一个 Solver 实例在适应 run 中跨局保留。`start_episode` 重置局内缓存，保留参数和任务内经验。正常调度顺序为：构造 Solver，`start_task`，若有产物则 `load`，随后重复开始局、决策、反馈、结束局。

Solver 自己决定在 `decide`、`on_transition` 或 `end_episode` 中是否开展学习。Runner 不强制每一步先调用 LLM，也不强制每局训练一次。

### 5.2 Context 的最小能力

```python
context.consult(request) -> ConsultResult
context.run_job(argv, resources=None) -> JobResult
context.emit(metrics) -> None
context.remaining_budget() -> dict
```

另提供工作区路径、运行模式、公开的任务初始化信息 `task_spec`，以及配置允许时的参考模拟访问。Context 不直接暴露真实环境对象。`emit` 用于 Solver 自报的预测或训练指标，不能改写真实得分与资源账本。

`consult` 是统一模型调用包装。返回值区分成功、额度耗尽和调用失败，让 Solver 决定下一步。开发、复盘和动作咨询都走相同包装。本地模块的前向计算不需要发起 `consult`。

`run_job` 同步运行本地命令，返回退出码、输出日志路径和耗时。命令执行期间游戏等待，Solver 保持常驻；训练结束后由 Solver 加载新产物。任务失败允许继续修复，已发生的时间仍计量。

V0 示例中的外部模型调用由 Solver 进程通过 Context 发出，job 用于本地计算。跨进程共享模型额度留到实际 agent 接入时扩展，不为此先建设独立网关服务。

### 5.3 ModelClient

必需提供确定性的 mock 实现，使所有自动验收不需要 API key。Mock 与真实调用在日志中显式区分。

ModelClient 返回文本、可取得的用量和耗时。真实 provider 适配可以先接一种现有可用服务；没有凭据时，记录“真实 API 接入未验证”，不伪造结果，也不阻塞其他 V0 验收。

所有调用预算和计量放在共用包装层，不能依赖每个 Solver 自行统计。Mock 输出只验证程序路径，不能用于报告真实 LLM 能力或延迟。

### 5.4 V0 的三个示例 Solver

| 示例 | 必须证明的能力 | 范围 |
| --- | --- | --- |
| `random` | 无 API、多局运行、固定种子复现。 | 极小随机策略。 |
| `reference_search` | 使用独立分支模拟后决策，统计模拟步数。 | 有限深度或少量 rollout 足够，不开发强 MCTS。 |
| `collaboration_demo` | 本地直接决策、mock 咨询、同步 job、模块更新、跨局保留与保存恢复。 | 人工写的接口测试程序，不代表自主开发能力。 |

协作示例必须有一个真正被后续决策读取的可更新小模块，例如收益估计表或一个标量预测器。用已观察的数据，通过同步 job 更新参数文件，加载新版本，并记录更新前后的值以及版本。不要只修改文件时间戳来模拟学习。

可以用测试配置强制触发咨询和更新时机，不必研究 router。该示例无需采用 RL、神经网络或获得更高分。参考搜索和测试调用规则都属于示例 Solver，不能写进 Runner。

## 6 Runner、预算与运行模式

### 6.1 一套实验循环

Runner 负责创建环境和 Solver、传递观测、执行动作、反馈结果、触发记录与 checkpoint。三个示例使用同一套循环。

每局的基本顺序是：

1. 用本局种子 reset 环境，调用 `start_episode`。
2. 将当前玩家观测交给 `decide`。Solver 可以同步咨询或运行 job，然后返回动作。
3. Runner 执行真实动作，记录转移，并调用 `on_transition`。
4. 自然终止或外部停止后，调用一次 `end_episode`，写入局结果。
5. 到达配置的保存节点时生成 checkpoint，然后开始下一局或结束 run。

同一转移只反馈一次；终局转移也必须送达 Solver。预算不足以再执行动作时，记录外部停止，不伪造一条环境转移。非法动作记录错误，可让 Solver 再决定；动作请求上限负责防止无限重试。

Runner 不在这些步骤中主动训练、不替 Solver 选择动作，也不在调用失败时免费请求另一个模型。

### 6.2 两个独立配置维度

| 配置 | V0 行为 |
| --- | --- |
| `mode = adaptation` | 同一 Solver 跨局持续运行，积累任务内经验和参数。 |
| `mode = evaluation` | 从指定 checkpoint 创建独立评测副本；每局重新从同一 checkpoint 恢复。 |
| `allow_learning = true` | 允许 Solver 更新学习模块与持久经验。 |
| `allow_learning = false` | 示例 Solver 停止参数更新与跨局经验写入；局内记忆和决策搜索仍可使用。 |

V0 必须跑通 adaptation 加允许学习、evaluation 加不允许学习两种组合。评测中的局内学习留给后续版本，但接口不要把 `evaluation` 永久定义成“禁止学习”。V0 收到尚未支持的组合时明确报错。

`allow_learning` 是实验契约，不是抵抗恶意代码的权限系统。不要通过禁止所有文件写入来实现：运行日志、局内缓存和搜索临时文件仍然需要写入。

### 6.3 基础预算

| 项目 | V0 需要实现的语义 |
| --- | --- |
| 真实动作请求上限 | 包含非法动作请求；到达上限后停止该 run，保留已取得的结果。 |
| 模型调用次数上限 | 额度在发起调用前检查；已发出的失败调用也占用次数，未发出的拒绝请求单独记录。 |
| run 墙钟时间上限 | 包含决策、咨询、job、保存等运行时间；不包括运行前的软件安装。 |
| 每局最大动作请求数 | 防止单局不结束，超过时标记该局 truncated。 |

模型额度耗尽只关闭新的模型调用，本地决策、搜索与训练可在剩余 run 预算内继续。Runner 不自动结束游戏。

V0 在所有 Solver 钩子前后检查时间，`consult` 和 `run_job` 发起前也检查，实际 timeout 不超过剩余运行时间。时间耗尽后不再发起新的模型调用或 job；已发生的转移仍反馈一次，结束回调只作收尾，局结果与停止日志仍落盘。

普通 Python 钩子采用协作式超时，不要求强制抢占；若返回时已超时，记录实际超出量并停止继续行动，不宣称实现了严格实时调度。模型调用次数是最小可执行硬额度；token 用量据实记录，未知值用 null，先不设计精细的 token 或 GPU 计费系统。

计量至少包含：真实动作请求数、成功环境步数、模拟步数（能取得时）、模型调用及拒绝次数、模型用量、job 耗时、决策耗时、run 总耗时。模拟步数与真实步数分开；第三方求解器自报的模拟量要标明来源。

决策耗时指从把观测交给 Solver 到拿到动作的端到端时间，包含这次决策内的咨询或 job；另外分项记录其耗时。不要把包含关系的耗时再次相加作为总成本。

### 6.4 不完整运行如何报告

自然结束时记录环境真实得分。超时、异常或预算截断时，真实最终得分可以为 null，并记录明确状态；不能把当前累计收益当作已经 BANK 的得分。

V0 同时报告请求局数、开始局数、完成局数及各类失败数。为便于检查，另报告一个覆盖全部请求局数的汇总得分：风险采集未完成或未开始的局按 0 计入这个汇总字段，并与真实得分字段分开。这只是测试环境的统计约定，不在 Runner 中写死为所有游戏的计分规则。

## 7 配置与任务表示

### 7.1 示例配置

下面给出 `configs/risk_collaboration.json` 的目标结构。实现时可以合并小字段，但 README 中的配置必须与实际程序一致。

```json
{
  "task": {"id": "risk_collect", "version": "1"},
  "solver": {"id": "collaboration_demo"},
  "mode": "adaptation",
  "allow_learning": true,
  "episodes": 6,
  "seed": 123,
  "capabilities": {"reference_simulator": false},
  "limits": {
    "max_action_requests": 100,
    "max_actions_per_episode": 16,
    "max_wall_seconds": 60
  },
  "model": {"provider": "mock", "max_calls": 1},
  "checkpoint": {"every_episodes": 2}
}
```

示例应通过确定性的测试安排，在额度内成功咨询一次，之后遇到额度拒绝，并继续本地决策；至少完成一次有效模块更新。这里的触发安排属于 `collaboration_demo`，不放进 Runner。若机器性能造成示例超时，可以调整墙钟上限并记录实际配置。

评测配置单独指定评测种子与每局预算，例如：

```json
{
  "mode": "evaluation",
  "allow_learning": false,
  "episode_seeds": [1001, 1002, 1003, 1004],
  "per_episode_limits": {
    "max_action_requests": 16,
    "max_wall_seconds": 30,
    "max_model_calls": 0
  }
}
```

评测的任务、Solver 与模型 provider 配置从 checkpoint 取得，评测配置只覆盖允许调整的预算和运行选项。局数由 `episode_seeds` 的长度决定。每个独立副本获得相同额度，不让第一局用完后续各局的预算。

### 7.2 留给后续任务的空间

Runner 将 Observation 与 Action 视为任务定义的可序列化数据，不依赖 `pot`、牌数量、棋盘宽度或特定动作编号。任务适配器负责解释和编码它们。

可以将固定棋盘拓扑、相邻关系、动作 schema 等放在任务初始化信息里；逐步观测只传变化的数据。无需反复生成冗长自然语言，也不要求所有游戏都是固定大小的矩阵。以后添加自然语言或图像视图时，从同一玩家可见信息生成。

V0 不开发隐藏卡牌、多模态和多玩家，但不要把完整内部状态定义成统一 Observation，也不要在 Runner 中假设观察足以还原全部状态。多玩家的调度与对手适应需要到实际任务出现后再设计。

## 8 记录、Checkpoint 与独立评测

### 8.1 最小运行目录

| 文件或目录 | 内容 |
| --- | --- |
| `config.json` | 本次实际生效的完整配置，包括默认值。 |
| `events.jsonl` | 带顺序号的环境、模型调用、job、版本更新、保存和停止事件。 |
| `episodes.jsonl` | 每局种子、状态、得分、步数及资源摘要。 |
| `summary.json` | run 汇总结果、资源、版本、错误和产物路径。 |
| `jobs/` | 子进程输出和训练产物。 |
| `workspace/` | Solver 的可变工作文件。 |
| `checkpoints/` | 可以单独恢复的系统产物。 |

不要求数据库。可增加必要的小文件，但不为同一数据维护多套独立账本。

真实转移至少记录 run、局和步编号、前后玩家观测、动作、reward、终止信息、Solver 产物版本和决策耗时。模型调用与 job 用事件编号关联到对应决策或局间阶段。

Solver 的候选动作、价值预测、置信信号或学习指标可以通过 `emit` 记录，明确放在 `solver_report` 类事件中。框架不要求所有算法都提供同一套预测信号，也不将这些自报值当作环境真值。

真实轨迹、调用量和运行时间由 Runner 写入；Solver 的笔记和模型放在工作区。V0 依靠清晰的代码职责划分实现，不建设防篡改日志平台。

### 8.2 Checkpoint 的内容与触发

V0 默认按完成局数触发 checkpoint，在 `end_episode` 返回且所有同步 job 完成后保存。周期由 Runner 控制，Solver 不能只挑表现最好的一刻作为唯一记录。每个保存点记录实际局数、步数和累计资源。

Checkpoint 至少包含：

- `manifest.json`：格式版本、任务和规则版本、Solver 类型与加载入口、实际配置、创建时进度及资源摘要。
- 可恢复的 Solver 产物：参数、持久经验、调用判断配置、必要训练状态与自身随机状态；未使用的部分可以没有。
- 本次使用的项目源码快照和依赖声明；若 Solver 生成了额外代码或提示配置，也纳入快照。小项目直接复制源码即可，不复制虚拟环境。

manifest 记录源码和产物标识，加载过程不依赖原工作区的绝对路径。局内棋盘、当前牌袋与上一局临时记忆不作为新评测局的初始状态。

恢复时必须使用 manifest 对应的源码版本。V0 可以要求当前安装源码与快照标识一致；不一致时明确报错，提示从快照重新安装。源码快照用于重建对应版本，不要求自动切换代码和依赖，也不开发多版本动态加载系统。

V0 的恢复保证是：在新进程中加载一个 checkpoint，开始新游戏并得到可复现的行为。不要求恢复任意 Python 进程内存，不要求从被打断的半局原位继续。

保存 Solver 对象的 pickle 文件不能替代源码、配置和加载契约；参数采用适合自身实现的格式即可。

### 8.3 独立评测流程

1. 读取 checkpoint 和评测配置，创建独立输出目录。
2. 对每个评测种子建立新的 Solver 工作副本，从同一 checkpoint 加载任务内产物。
3. 清空局内状态，运行该局，记录真实表现及在线资源。
4. 丢弃副本的可变工作状态，汇总结果，不写回原 checkpoint 或适应 run。

评测不把测试结果反馈给原适应进程。将来用开发集选择最优权重时，可以另设开发评测；最终测试集不能同时承担选模和最终报告。

在相同 checkpoint、种子、mock 和预算下，两个新进程的动作与分数应一致；墙钟时间无需逐字一致。评测前后原 checkpoint 的内容摘要应不变。

V0 保存全部预定 checkpoint，至少选一个完成恢复与独立评测，报告其真实表现、在线调用与延迟，以及此前累计的适应投入。逐保存点评测曲线、完整的多预算矩阵、统计置信区间与成本回本分析留到 V1。

## 9 命令行与人工交互交付

以下为目标命令。要求最终 README 提供经过实际运行的等价命令，不要求拘泥于命令名称。

```bash
python -m pip install -e '.[dev]'
python -m pytest -q

python -m boardbench run --config configs/risk_random.json --out runs/random_demo
python -m boardbench run --config configs/risk_search.json --out runs/search_demo
python -m boardbench run --config configs/risk_collaboration.json --out runs/collaboration_demo

python -m boardbench evaluate --checkpoint runs/collaboration_demo/checkpoints/ep_000006 --config configs/risk_eval.json --out runs/eval_demo

python -m boardbench play --config configs/risk_play.json
python -m boardbench replay --trajectory runs/collaboration_demo/events.jsonl
```

运行命令结束时打印状态、结果文件路径和 checkpoint 路径。输出目录已存在时明确报错或要求显式覆盖，避免无意拼接两次运行的轨迹。

`play` 启动本地页面，给出可打开的地址。页面只需展示当前收益、剩余牌、动作结果与最终得分，并支持 DRAW、BANK、新局。

`replay` 可以复用同一页面，提供选择局和前后步按钮，根据记录中的观测显示状态。回放无需 Solver、模型凭据或重新运行随机抽牌。

UI 后端使用同一真实引擎；UI 展示与 RL 编码可以不同，但不能各自实现规则。无需另建复杂前端工程。自动测试以 headless 接口为主，另做一次实际页面操作与回放检查，保留截图或简短说明。

## 10 实施顺序

| 步骤 | 开发内容 | 结束时必须能看到的证据 |
| --- | --- | --- |
| M1：真实闭环 | 风险采集、公共类型、随机 Solver、基本 Runner 和日志。 | 固定种子多局运行，真实转移与得分可核对。 |
| M2：常驻协作 | Context、mock 模型、预算、同步 job、可更新模块。 | 无 API 路径、咨询成功与拒绝、有效更新后继续决策，跨局状态保留。 |
| M3：恢复和评测 | 完整 checkpoint、独立副本、evaluate。 | 新进程从保存点开始新局，固定种子复现，原产物不被修改。 |
| M4：训练与搜索入口 | RL 薄适配、参考搜索与独立模拟随机流。 | 两种接口共用引擎，搜索不改变真实后续随机结果。 |

M4 和 UI 可以在公共接口稳定后并行。每步优先完成可以运行的纵向流程，不先建立大量空类或占位服务。

少量实现选择记录到 `docs/decisions.md`：只写对后续兼容有影响的决定，例如动作错误协议、随机种子派生、checkpoint 布局。普通变量命名和小函数拆分无需记录。

## 11 V0 验收表

下表是验收行为，不要求一行对应一个测试文件。避免重复测试相同实现细节。

| ID | 必须验证的行为 | 建议证据 |

| A09 | 完整系统可以在新进程、不同工作目录中恢复，新局不继承旧局棋盘；加载时检查源码版本一致。 | 子进程加载 checkpoint 与版本不一致报错的实际测试。 |

V0 验收不要求分数领先、不要求模型更新后一定变强、不证明 agent 已经能自主编程。它只证明以后开展这些实验时，关键系统路径可运行且可检查。

## 12 回传审阅包与本地 Agent 工作要求

### 12.1 完成后回传什么

提交一个可直接解压检查的 ZIP，包含：

- 源码、`pyproject.toml`、依赖锁文件或明确版本范围、README、本实施规范和实际接口说明。
- 全部小型配置、测试，以及 `IMPLEMENTATION_STATUS.md`。
- 三个示例 Solver 的代表性运行记录；协作示例至少一个完整 checkpoint；从它产生的独立评测结果。
- 实际执行过的安装、测试和运行命令与输出摘要；Python 版本及 CPU 等基本运行信息。
- UI 和回放检查记录，建议附一张截图。

不打包虚拟环境、缓存、大量重复 rollout 数据或 API 凭据。保留的示例产物应足以复查，不需要上传每次调试的全部输出。

`IMPLEMENTATION_STATUS.md` 至少使用以下列逐项对应 A01–A12：

| 验收 ID | 已通过／未通过／未验证 | 实际命令或检查方式 | 证据路径 | 已知问题 |
| --- | --- | --- | --- | --- |
| A01 | 按实际填写 | 按实际填写 | 按实际填写 | 按实际填写 |

文件存在不等于行为通过；未执行的步骤标注“未验证”。若有偏离本文但更简单的实现，写出行为是否等价及原因。日后审阅重点是接口边界、真实执行记录、恢复和评测可复现性，以及 V1 是否能通过添加环境和 Solver 接入。

### 12.2 可以直接交给本地 Agent 的任务说明

> 按本规范实现 V0，从 M1 开始逐步完成。只实现风险采集测试环境与三个小型示例 Solver，完成公共实验流程、预算和记录、同步 job、完整 checkpoint、独立评测、RL／搜索薄适配及简单 UI。不要提前实现 V1 游戏、强 RL、Harbor 集成、分布式执行或安全平台。普通工程选择自行决定，并只记录影响兼容性的决定。实际运行验收，整理证据与已知问题，最后生成可回传检查的 ZIP。全部核心验收使用 mock，不因缺少 API key 停工。若某项无法验证，明确写出，不能用占位输出宣称完成。
