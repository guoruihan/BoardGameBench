# V1：Baseline、网页交互与交付验收

本文规定三个单人环境 `micro_tiles`、`take_it_easy`、`harmonies` 的求解实验与产品交付。Harmonies 默认配置为官方单人模式、A 面、基础动物牌，自然之灵关闭；采用交付包中的规则版本和末袋裁定。

V1 的目标是完成可信环境、实际可运行的预设求解方法和人类交互网页，并测量得分与计算消耗。自主开发、训练和选择调用方式的通用 agent 属于 V2。V1 不需要 LLM、远程模型 API、远程部署或分布式运行设施。

## 1. 每个环境实现哪些方法

每个环境控制在 3–5 类方法内。默认实现下列四类；已有方法的超参数、搜索预算和训练 checkpoint 不计为新的方法类别。

| 方法 | 要求 | 用途 |
| --- | --- | --- |
| Random | 从当前合法动作中采样；随机数与真实环境随机数独立 | 最低参照、覆盖合法动作 |
| Heuristic | 清晰记录特征与决策规则；没有训练参数更新 | 测量直接规则的能力 |
| Monte Carlo search | 用公开信息构建采样未来，给定明确搜索预算 | 测量增加在线计算的收益 |
| One RL method | 一个可复现训练流程，真实更新参数并保存 checkpoint | 测量参数学习和快速推理的效果 |
| Value/policy + search（可选） | 仅在前四类完成且有明确收益假设时加入 | 测量学习是否改善搜索效率 |

不要一次实现多个相近 RL 算法。可以使用项目已有 RL 依赖与实现；若需新选型，支持 action mask 的 PPO 是可选起点，不是强制协议。RL 的网络和动作编码可因游戏而异。

Random 在 Harmonies 中按合法微动作采样会受动作枚举方式影响。应明确其采样层级，例如先采样动作类型、再采样参数；同一实验保持不变。不要把“先完成卡牌再选资源”等策略性偏好悄悄写进随机基线。

推荐的首批方法设计：

| 环境 | 启发式起点 | 搜索起点 | RL 起点 |
| --- | --- | --- | --- |
| Micro 3×3 | 即时邻接收益与行列潜在收益 | 小状态 expectimax 或采样 rollout；局部可精确求解状态用于校验 | 小 MLP 与固定动作 mask |
| Take It Easy! | 各方向未破坏直线的预期收益 | 从剩余牌集合采样后续牌，有限预算 rollout 或树搜索 | 小 MLP/图编码器，19 个放置动作 mask |
| Harmonies | 地形分数、动物牌完成进度与剩余空间 | 在微动作树上搜索，或由求解器生成合法回合候选后搜索 | 对当前合法动作候选打分，或采用带 mask 的分层动作策略 |

上述均为待实现、待验证的方法建议，不代表已有实验结果。Harmonies 的启发式候选裁剪、回合动作生成器属于求解器；引擎应保留完整合法动作，避免改变游戏规则。

## 2. 开发与实验顺序

对每个游戏先完成并验证环境与人类手动交互，再做基线实验，最后把真实策略产物接入网页。三个游戏可分别推进，不必等待最复杂游戏完成后才验收简单游戏。

### 2.1 Smoke 阶段

目的为发现接口、动作、训练和恢复错误，不用于结论排名。

- 用多局随机行为跑通 reset、终止、得分与动作合法性。
- RL 至少执行一次真实参数更新，记录更新步数、训练样本数及参数或 checkpoint 哈希变化。
- 保存后重新启动进程加载 checkpoint，完成新局推理。
- 小批固定种子评测能产出逐局记录和汇总表。
- 网页至少可以手动完成一局，并播放一个策略的完整回放。

“训练脚本可以启动”不等于 RL 已完成；以实际发生更新和可恢复推理为准。

### 2.2 Pilot 阶段

- 先为每类方法指定有限的本地计算预算、训练步数或局数、最大墙钟时间。
- 建立一个能超过随机策略的启发式或搜索参照；如未达到，应先检查规则、计分和方法实现。
- 对同一 RL 代码版本保留未训练 checkpoint 与至少两个训练进度 checkpoint。
- 使用验证种子比较训练进度与搜索预算，选择网页候选产物。
- 记录瓶颈：环境吞吐、模型推理、合法动作生成、搜索或训练。

可以从 1 个训练随机种子、32 个验证局面和 128 个测试局面起步；这些是可配置的起始规模，不是保证统计稳定性的标准。测试集应在本次候选选择结束后才用于最终评估。

### 2.3 扩大实验

只有在 pilot 证明方法正常、训练有信号或存在明确可修复问题时，才逐级扩大预算。预算可以按约 4 倍递增，具体上限由实验配置固定；不要为追求分数无限延长训练。

用于正式比较时，建议至少 3 个独立训练随机种子，并扩大统一测试种子集合。多局测试只能估计某个 checkpoint 的表现；多个训练种子用于估计学习过程本身的稳定性，两者应分别报告。

若资源只允许单次训练，可以交付可复现的 pilot 结果，但必须明确标为单次训练结果。没有可信公开对照和相同规则、预算的验证，不宣称达到 SOTA。

## 3. 数据划分与评估口径

### 3.1 三套种子

明确保存 `train`、`validation`、`test` 三套环境种子或确定性生成配置。三者不重叠；训练随机种子、环境随机种子、求解器随机种子分别记录。

- 训练：交互与参数更新。
- 验证：选择 checkpoint、启发式参数、搜索预算和网页难度。
- 测试：对冻结的候选集合进行最终报告。

不根据测试集分数选择“最好”的 checkpoint。若查看测试结果后继续调参，后续结果应说明该测试集已参与开发，并另设最终测试集。

### 3.2 真实得分与奖励

主指标为环境规则定义的最终得分。分项得分可用于解释策略行为。

训练可采用终局奖励、分数差分或其他 shaping，但 shaping 由训练 wrapper 提供，需记录公式与系数；网页分数和测试报告仍显示规则得分。不得把 shaped return 当作官方游戏分数。

Harmonies 中一个回合包含多个决策。训练需明确折扣应用于微动作还是游戏回合，避免因额外拿卡、放动物等操作而无意改变优化目标。最小实现可以采用有限局长、终局得分和 `gamma=1`；采用其他设置时记录理由。

### 3.3 比较指标

每个方法至少报告：

| 指标 | 口径 |
| --- | --- |
| 游戏得分 | 测试局数、均值、标准差；可附配对差值区间 |
| 在线延迟 | 决策延迟 p50/p95、每局求解总时间；固定硬件与线程配置 |
| 搜索预算 | 每个决策/回合的节点数、rollout 数或时间上限，并记录实际消耗 |
| 训练投入 | 环境步数与局数、梯度更新数、训练墙钟时间、设备与并行环境数 |
| 模型与产物 | 参数量、checkpoint 大小、代码版本和配置 |
| 运行异常 | 非法动作、超时、崩溃及未完成局的数量和处理方式 |

本地 CPU/GPU 推理也计入计算消耗。首次模型加载时间可单列，常驻模型的决策时间另报；浏览器网络与绘图开销不混入纯求解时间，另报网页端到端响应时间即可。

比较 RL 的训练前后性能时，固定代码、网络、预处理、动作编码和评测预算，只改变权重。代码迭代带来的提升另列。保存未训练版本可以支持这一对照。

不预设“RL 必须胜过搜索”。训练无收益、搜索更强或启发式已足够的结果均应如实记录；不得用手写动作代替模型输出，却标为训练后的策略。

## 4. 不可见未来与搜索模拟

求解器只接收当前玩家可见信息和允许的公开历史。不能通过游戏 seed、真实随机数状态或完整牌堆排列读取将来结果。

- 真实游戏的随机流与搜索随机流独立。
- Take It Easy! 搜索根据公开剩余牌集合重新采样未来，不复制真实抽牌顺序。
- Harmonies 搜索根据公开状态和剩余资源信息建立可能未来，不读取未公开动物牌或资源顺序。
- UI 提示与 bot 使用同一观测边界。
- 同 seed 对局可以用来降低比较方差，但不能把种子交给策略当作预测未来的输入。

精确恢复真实对局的完整 snapshot 可以保留真实随机数状态。搜索用的模拟状态应另有明确入口；不要把含真实未来信息的恢复 snapshot 直接送给求解器。

## 5. 预训练策略与难度

网页必须加载实际存在、可复现来源的策略产物。RL 应加载训练得到的权重；搜索策略应加载固定配置，必要时加载训练价值模型。演示数据、随机动作或占位文件不能冒充已训练策略。

每个可选策略提供 manifest，最少包含：

```json
{
  "policy_id": "unique_stable_id",
  "environment_id": "take_it_easy",
  "rules_version": "project_defined_version",
  "method": "rl",
  "code_version": "commit_or_source_digest",
  "config_path": "relative/path/to/config.yaml",
  "artifact_path": "relative/path/to/checkpoint",
  "artifact_sha256": "actual_file_digest",
  "training_steps": 0,
  "training_seed": 0,
  "selection_split": "validation",
  "validation_summary_path": "relative/path/to/summary.json",
  "inference_device": "cpu"
}
```

示例中的数字和路径是字段说明，生成 manifest 时必须填入真实值。非学习方法使用 `null` 表示不适用的训练字段，并提供其配置文件哈希。

难度不是随机标签：

- 依据统一验证集合的实际得分排序，结合延迟选择网页的 easy / medium / hard 候选。
- 候选可来自不同方法，也可来自同一方法的不同训练 checkpoint 或搜索预算。
- “最高难度”是当前交付产物中的验证最强候选，不是全局最优的声明。
- 如果未形成可信的三个强度档，先展示“随机 / 启发式 / RL / 搜索”等真实方法名与验证均分，明确缺少强度分层；不要硬凑三级。
- 三个档位不需要三个独立训练流程，但每个档位必须对应可复现的具体产物与推理预算。

## 6. 本地网页

交付可构建的前端和一个轻量本地后端。前端生成静态 build，后端负责游戏会话、模型常驻加载和求解调用。项目可以统一通过一个本地 `serve` 命令提供二者。

不要求所有模型在浏览器内推理，也不要求纯静态离线运行。无需云部署、登录、账号系统或远程数据库。

### 6.1 同一引擎

RL、搜索验证、人类点击操作和回放都使用同一规则引擎。前端只做交互呈现与合法操作引导，不另写一套决定最终结果的计分逻辑。

非法点击由引擎拒绝并返回可理解原因；不要静默改为另一个动作。预览、高亮与提示不能推进真实游戏随机数或修改棋盘。

### 6.2 四类交互

| 模式 | 最小行为 |
| --- | --- |
| 自己玩 | 开新局、选择配置、执行动作、看到终局分项得分 |
| 看策略 | 选择实际策略，逐步或自动播放，可暂停与查看动作 |
| 提示与接管 | 对当前真实局面请求建议；用户可采用或拒绝；bot 可从当前状态继续，之后可还给人类 |
| 同 seed 挑战 | 人类和策略从相同初始随机条件各自玩一局，结束后比较得分与回放 |

提示只返回建议，不自动执行动作。接管保留当前局面和回合中间状态，不重新开局。一次局内切换通常无需训练；策略为 V1 的预设产物。

同 seed 不保证 Harmonies 每轮动物牌市场完全一致：拿牌和换牌操作会改变后续牌何时公开。UI 应称“相同初始随机条件”，不能承诺全过程同牌面。挑战进行中不要展示对方未公开未来的完整回放或终局棋盘。

### 6.3 各游戏的最小显示

| 游戏 | 显示要求 |
| --- | --- |
| Micro 3×3 | 棋盘、两枚供选资源、当前步、合法落点、邻接与行列得分 |
| Take It Easy! | 19 格棋盘、方向正确的当前牌、空格、各方向完整直线与得分解释 |
| Harmonies | 23 格棋盘、堆叠高度与层内容、三组资源、三张公开动物牌、持有与完成动物牌、待放资源、动物位置、分项得分 |

Harmonies 须分别显示“第几回合”和“当前动作”；拿牌、资源放置和动物放置可交错，网页不能强制改成不符合规则的线性流程。可用 2D 六角格、数字高度与层查看，不要求完整 3D 场景。

动物牌可以先用图案、分数与文字生成清晰的程序化卡面；不要让缺少美术效果阻塞规则与训练。合法落点和动物图案高亮应来自引擎返回的合法动作。

## 7. 实物交付清单

每个环境交付：

1. 环境实现、规则配置及版本、可解释计分、保存与恢复入口。
2. 人类操作页面与共享引擎的本地运行入口。
3. 3–5 类以内的求解方法和统一推理适配；默认四类。
4. 可重复执行的训练命令、验证命令、测试命令及其配置。
5. 至少一个真实 RL checkpoint，以及相同代码版本的未训练对照 checkpoint。
6. 可供网页加载的策略 manifest、实际文件和验证结果。
7. 每局原始结果、汇总结果、成本记录，以及至少一个可重放的完整对局。
8. 简短实验报告：实际完成了什么、哪些方法更强、耗时如何、哪些结论仍不确定。

共享交付还包括前端 build 命令、本地 serve 命令、依赖安装方式和 README。用户应能从干净进程按 README 加载已有策略并玩一局，无需重新训练。

训练权重较大时可单独存放于明确的产物目录，但本次本地交付必须包含可用路径和实际文件；只提供“以后会下载”的占位链接不算完成。不要把大规模原始训练轨迹默认打进交付包；保留必要配置、汇总、模型和少量代表回放即可。

## 8. 验收与完成状态

按游戏分别记录下面三层状态，不以一个总勾选掩盖未完成部分。

| 状态 | 必须满足 |
| --- | --- |
| 环境完成 | 关键规则与计分测试通过；随机局能完成；固定种子动作回放一致；人类能完整玩一局 |
| 实验完成 | 预设方法可运行；RL 发生真实参数更新；固定代码训练前后测量；独立测试结果与成本记录齐全；checkpoint 可重新加载 |
| 展示完成 | 网页四类交互可用；策略来自真实产物；方法/难度名称有验证依据；人类与 bot 得分由同一引擎计算 |

重点验收错误风险：

- UI、训练和回放之间同一动作序列得到相同状态与最终分数。
- 保存后恢复回合中间状态，尤其 Harmonies 待放资源与已使用的拿牌机会。
- 搜索和提示不会消耗真实抽牌随机流，也不会读取真实未来。
- RL checkpoint 不是随机初始化的副本；实际推理路径使用该权重。
- 未完成或出错的局不从结果中悄悄删除。
- 验证集选择产物，测试集只评估冻结候选。

验收不写死分数门槛，不要求每个游戏中 RL 都超过启发式。若训练没有改善或未形成多个强度档，工程结果仍可如实交付，但报告必须标明“尚未验证学习收益”或“难度分层未完成”，并给出已经尝试的预算与诊断。禁止编造实验结果来满足阶段目标。
