# V175 三组工具直接对局：运行设置与资源消耗

核对日期：2026-11-14。统计对象为 `outputs/v175/direct_play_20261101/` 中已经停止的历史任务。
本次重新读取逐局结果和逐调用响应，**没有恢复对局或发起新的模型调用**。

可确认的量级是：三组共发起 **17,098 次调用**，返回记录合计约 **3.02 亿 token**；
241 局有效完成。裁判／对手主进程合计 **31.70 CPU 核时**，没有使用本地 GPU。
外部模型推理 GPU、CLI 子进程 CPU 和真实账单没有完整计量，不能把 31.70 核时说成全部计算成本。

## 1. 当时具体怎么跑

### 1.1 工具与模型

| 组合 | 工具版本 | 模型及设置 | 使用方式 |
| --- | --- | --- | --- |
| Codex | 0.163.0 | GPT-6.1 Sol，沿用本地 `xhigh` | 已有本地登录；每次决策新上下文 |
| OpenCode | 1.19.5 | DeepSeek V4.1 Flash 1017 | 已有 API 配置；每次决策新上下文 |
| Claude Code | 2.1.288 | Claude Opus 5.5，沿用本地默认 | 已有本地登录；每次决策新上下文 |

这是三个“工具＋模型”组合，不是三工具乘三模型的九组交叉实验，不能独立归因工具效应。
规则目标是**赢得对局**，不是只最大化自己的绝对分数。
具体服务地址、认证、账号身份、CLI/API 接线脚本和私有费率均不进入 Git。

### 1.2 对局矩阵

- 16 个正式双人游戏，Five Tribes 不在本轮。
- 每款对 `legacy` 学习策略和 `search_900` 搜索策略各四局。
- Century Spice Road、Clever、Patchwork、Toy Battle 再对 `candidate` 学习策略各四局。
- 四局为两个探索 seed × 两个座位，0 号位先手；三组工具共用初始 seed 和座位安排。
- 每工具 `16×2×4 + 4×4 = 144` 局，三组合计 **432 局**。
  每工具其中 64 局是搜索对手、80 局是学习对手。

`candidate` 包括模仿初始化保留下来的模型，不应把全部候选改善称为 PPO 提升。
Harmonies 用胜负目标的 `search_900`，未额外加入自身得分目标的 `search_score_900`。
配对 seed 不保证不同策略整条轨迹的未来抽牌逐次相同。

### 1.3 一个模型决策的调用链

```text
裁判建立当前座位的公开观察与完整合法动作
  → 只有一个合法动作：自动执行，计入强制动作，不调用模型
  → 否则：启动该工具的独立 CLI 调用
      输入：任务指令 + 完整规则 + 静态组件目录
            + 当前观察/公开历史 + 全部合法动作列式表
            + 上一步最多 2000 字符的私人计划
      输出：JSON {action_index, memory}
  → 检查动作行号和格式；必要时最多再尝试一次
  → simulator 执行动作，记录轨迹，再轮到另一方或下一原子选择
```

模型不能调用文件、模拟器、搜索或其他工具，也不写策略程序。返回的是一个**原子动作**，
不是提前给出一整局动作序列。选牌、放置、支付、额外动作等都可能各占一次模型调用。
合法动作未作启发式裁剪；输入不含私有 snapshot、未知牌序、对手暗手或 RNG。
两次都不能给出合法回答则保留失败结果，不用启发式代走。

因此，这轮成本衡量的是“持续让 LLM 亲自走棋”。它不等于“让开发 agent 编写策略，
再让本地策略批量训练／评测”的成本。后一种流程不需要每个环境 step 都访问模型。

这些行**不能相加**：搜索已经在主进程里执行；CLI 等待已经包含在单局墙钟里。

`parent_cpu_seconds` 使用 `time.process_time()`，包含该对局主进程中的模拟器、
bot、搜索和请求准备等 CPU；不包含 CLI 子进程的 Node/Python 等启动、序列化、认证消耗，
也不包含远端模型推理。计时还不覆盖进入对局循环前的部分加载开销。
GPU=0 只说明我们控制的运行 worker 没用 GPU，不说明外部模型推理免费或不需要 GPU。

按对手分组，**纯学习对手的所有对局尝试合计仅记录 167.80 秒主进程 CPU**，
其余约 31.65 核时来自含 `search_900` 对手的对局尝试。
这表明这轮本地主要计算负担是长预算搜索，LLM 对学习 bot 的对局主要受响应等待限制。
167.80 秒同样不含 CLI 子进程，不能当作重新部署整个系统的完整机器成本。

24 个 worker 若整个最长窗口都占满，是约 289.43 个核槽小时的配置上界；
逐局活跃墙钟实际合计 160.04 小时，已记录主进程 CPU 只有 31.70 核时。
**24 核×12 小时不等于实际烧掉了 288 CPU 核时。**
同时，固定把等待 API 的进程长期绑住一个调度槽，仍会占用并发配额，影响整体吞吐。

## 6. 为什么消耗高

### 6.1 原子决策数量

El Dorado、Stone Age、Dominion、Targi 的完整一局往往需要上百次模型决策。
“每个对手四局”听起来少，但乘以原子动作、36 个游戏／对手组合和三个模型，
最终就产生一万七千多次请求。把游戏都视为与 Toy Battle 同样长度会严重低估成本。

### 6.2 反复发送静态规则和随局增长的历史

每步都是新上下文，重复发送规则、牌表和完整当前观察。
已有 prompt 审计显示（**以下是 JSON 字符，不是 tokenizer token**）：

- Harmonies 一次开局输入约 27,127 字符，其中规则 5,023、静态组件 18,187。
- Patchwork 一个开局输入约 52,937 字符，1,057 个合法动作的表占 31,860 字符。
- Dominion 的一个抽样后段输入约 35,942 字符，仅观察／历史就占 24,137。

这些是抽样位置，不是所有局的最大值。规则文本还包含工程／覆盖说明，
后续可以另写完整但精简的“玩家规则”，避免每步重复发送对当前决策无帮助的工程说明。
不能为了省 token 删除必须知道的牌效果或暗中剪掉合法动作。

### 6.3 推理输出与缓存

DeepSeek 的输出中 **94.93% 是推理 token**，不是最后那段动作 JSON；
Codex 相应比例为 **85.25%**。只统计可见答案会大幅低估输出消耗。

输入缓存读取占比：Codex **37.51%**，DeepSeek **0.00936%**，Claude **0%**。
Claude 记录了大量缓存写入，却没有缓存读取。新上下文本身不必然让缓存失效，
实际还取决于 provider 和前缀稳定性；应实测缓存命中，不能只根据“支持 cache”来估价。

## 7. 金额能估到什么程度

**DeepSeek 有当时保存的费率和用量，可以算历史估计；Codex 和 Claude 没有逐调用实际账单。**
为保持私有服务资料边界，公开仓库只保留 token 和以下通用公式；
当时的网关费率、金额及分项估算保存在本地不入 Git 的
`outputs/v175/resource_audit_20261114/Private_Cost_Estimate_zh.md`。

若费率单位为“货币 / 百万 token”：

```text
估计费用 = 未缓存输入 / 1e6 × 未缓存输入单价
         + 缓存读取 / 1e6 × 缓存读取单价
         + 缓存写入 / 1e6 × 对应写入单价
         + 输出总量 / 1e6 × 输出单价
```

这轮 DeepSeek 的输出总量为 20,938,209，包含推理，不是只有 1,062,368。
Codex／Claude 的 thinking 已含在输出总量中，不再加一次。
订阅额度不能直接拿普通 API 标价当实付；也不能因为工具显示 `cost=0` 或已有登录就说免费。
CPU 货币成本还需要实际机器核时单价；外部模型 GPU 成本不能从现有日志推导。

## 8. 对后续 benchmark 的具体含义

### 继续测“LLM 直接玩”

先按**每个游戏**的调用量估预算，再乘模型、对手、座位和 seed 数；先解决限额识别，
达到配额应暂停该组合，不能继续扫完队列制造上百个失败。
先用冻结学习对手完成小批校准，900 秒搜索只放在选定的小面板作为强参考。

若保留原矩阵，每模型 64 局搜索对手理论上最多消耗 16 搜索小时，三模型最多 48 小时；
实际这一轮为 31.64 搜索墙钟小时，主要因为部分局提前失败或未完成。
把搜索预算从 900 改小会改变对手强度和对局长度，不能假设只是费用等比例下降。

输入压缩、稳定静态前缀、缓存、限制推理长度值得独立试验；若改变可用工具或动作表达，
应发布新的直接对局协议。降低 token 不保证保持原策略质量。

### 测“agent 开发和训练策略”

更合理的调用链是：

```text
LLM 阅读规则 → 编写／修改本地策略或训练脚本
  → 本地程序批量执行 GT 交互与训练
  → 返回小型汇总、必要失败轨迹、分项指标
  → LLM 决定下一次修改
  → 冻结策略，裁判独立测试
```

此时 LLM 调用数主要随开发／调试轮数增长，而不是随游戏动作数增长。
**不能用这轮 0.8–1.3 M token/完整局，直接乘未来 RL 的数百万环境 step。**
也不能据此保证开发 agent 一定便宜：长上下文调试和无限制重试同样可能消耗很多。

建议下一次把 LLM token／费用、GT reset／step、裁判 CPU、开发 CPU/GPU、最终推理时间
分别设限和记录。已有文档中的 `8 CPU + 1 GPU` 可以作为开发资源配置候选，
但这轮没有实际测这种开发 setting，不能据此给出可靠的训练完成时长。
先做一个有明确预算的小型开发试跑，用实测的“每轮 token＋采样吞吐＋训练时长”校准。

## 9. 复算方法与证据

公开审计脚本只读历史记录，不读适配器配置、不调用 API、不启动 simulator，不输出回复正文或原始连接路径：

```bash
PYTHONPATH=src .venv-train/bin/python scripts/audit_v175_resources.py \
  --root outputs/v175/direct_play_20261101 \
  --out outputs/v175/resource_audit_20261114/audit.json
```

原运行目录保持不变，审计输出要求放在原目录之外。统计包括全部计划任务，
不存在结果的任务显式列为未启动；缺响应和缺 usage 分别计数，不自动补零后声称完整账单。
有 raw call identity 的记录检查去重；三个 usage schema 均校验包含关系。

证据入口：

- 原目录 `launch_manifest.json`、`schedule.json`、`deadline.json`：源码、矩阵、并行与窗口。
- `matches/*/result.json`、`call_*.request.json`、`call_*.response.json`：逐局时间和逐调用 usage。
- `summary.json`、`queue_finished.json`、`user_stop.json`：停止时的整体状态。
