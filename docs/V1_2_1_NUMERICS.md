# V1.2.1 / 0.4.3：批大小数值漂移修复

## 故障与直接复现

0.4.2 已先上传为 `32d0c66`，包含四格×三种子1000万动作开发结果及已知停止状态。
之后才修改数值实现；历史源、日志、模型和失败现场不改写。

原批次 `outputs/v121/factorial_batched_20261004_b` 在 E11_T16_913 的第12409批停止。
失败现场：`training/E11_T16_913_a20000000_chunk00138/probability_failure.pt`。
网络FP32，概率归一化已是FP64；采样前向批大小1–16，更新前校验为918行。
在同一 b35 GPU5、PyTorch2.4.1+cu121、TF32矩阵乘关闭下，固定权重/输入重现：

| 网络前向 | 相对原始行为概率最大比率误差 | 与同精度batch1之间最大误差 |
|---|---:|---:|
| FP32，batch1 | 1.311323e-4 | 0 |
| FP32，batch16 | 6.493146e-6 | 1.376074e-4 |
| FP32，batch256 | 1.411074e-5 | 1.170062e-4 |
| FP32，batch918 | **1.763686e-4** | 4.523035e-5 |
| FP64，batch918 | 8.807132e-5 | **2.109424e-14** |

同形状重复前向结果完全相同；不是通过重试随机消失的错误。
FP64对所有batch大小1/2/4/8/16/32/64/128/256/918，跨形状误差最多约2.1e-14。
这定位到成熟网络的FP32前向对批大小敏感；仅将最终概率归一化升精度并不足够。
PyTorch也明确不保证批处理与逐样本浮点结果逐位相同，见
[官方数值精度说明](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html)。

证据：`outputs/v121_checks/numerics_20261004/replay.log`；可复现脚本
`scripts/diagnose_v121_probability.py`，必须在已预留GPU上执行。
首次执行包含初始化，短前向测量仅用来排除数量级退化，不当作严格吞吐对照。

## 修复边界

新增 E00_T16_F64 / E01_T16_F64 / E10_T16_F64 / E11_T16_F64，各以原T16配置为父。
网络参数、前向、梯度和Adam矩使用FP64；原始公开编码缓冲仍FP32，进入网络时转换。
初始化先使用相同FP32抽样再无损提升，导入也保留旧参数及Adam矩的数值。
原始编号和权重加载保持不变。输入/合法mask/STOP/MC回报/批16局/PPO超参数不变。

不放宽1e-4门槛、不重写旧log-prob、不丢弃不一致样本。
真实故障CUDA回归直接把相同参数及同一批原始行交给 `_update`：原FP32必失败，
FP64以8.8071e-5通过并实际完成有限梯度更新；随后新采样将全程使用一致FP64前向。
另有错误log-prob注入测试，确认FP64仍会在更新之前拒绝真实不一致。

FP64是明确的数值变种，不是对跨源码逐位一致的承诺；也不声称改善分数。
三秒CPU评测可能受推理速度影响，后续成绩仍以同预算重新实测为准。

## 审计续训

从停止的父批次逐个选择最大 `(动作数, 优化器更新数, 批数)` 的完整检查点，
包括失败阶段有效的rolling checkpoint，以及兄弟进程收到停止信号后写出的final。
不按开发分数挑模型；损坏的最高进度文件会报错，不能默默退回旧点。

新批次必须使用新目录和冻结源码。`recovery.json` 固化旧源/配置/文件哈希、父动作数、
旧曲线和成本；每个新检查点继续携带 `lineage`。参数、优化器、随机状态和计数器保留，
失败后未写入完整检查点的少量工作不保留，但原GPU开销不减掉。新更新只用重新采集的完整局。
`--resume` 的严格同源/同配置检查没有放开。

父批次GPU成本90481.685秒（25.1338GPU小时）继续计入该恢复线；新阶段资源另加。
此前串行/吞吐试验以及本次数值诊断都有独立产物；恢复线小计不等于项目从开始以来的总成本。
诊断不是正式学习曲线，测试checkpoint不被挑选为恢复起点。
