# GPT-6-Astra 如何逐步开发 Harmonies 策略

这份记录展示被测 Agent 在 c3 中实际执行的开发过程，依据命令日志、程序快照、实验文件和 GT 成绩整理。它是可核查的行动记录，不是事后设计的理想流程。基础设施配置与后续评测另列，避免混成 Agent 自己的策略改进。

## 先看完整路线

读取公开规则与预算 → 实现 C++ 三资源联合搜索 → 首局调通并保存检查点 → 自建模拟器 → 调整动物潜力与搜索宽度 → 加入下一回合前瞻 → 验证终局动物分配 → 跑完 10 局开发 → 最终封装未赶上输入额度 → 用早期有效检查点评测。

本次没有训练 RL。Agent 自己选择了“编写搜索程序，再用实验修改程序”的路线。它用了约 34 分钟、81 次模型生成、198 万输入 token 和约 8,936 核秒；最后用于评测的程序不需要在线调用模型。

## 1. 读规则，确定策略形式

**日志：`item_0`–`item_7`。**

Agent 先读取开发/部署预算、SDK、公开规则和动物卡目录，启动第一局，查看真实观察与合法动作。沙盒没有 `rg` 时，它改用 `find`，没有请求修改宿主机。

它随后选择联合规划一个回合的三个资源，而不是每次只评估一个落点；估值同时考虑地形得分和动物图案离完成还有多远。这里的选择有明确的部署目的：把主要工作写进编译程序，避免每步消耗模型调用。

首局包含 SDK 调试阶段直接发出的动作，因此不能把首局全部行为描述成最终程序的独立表现。

## 2. 写出第一版可执行搜索器

**日志：`item_8`–`item_16`。**

它生成 `catalog.h`，将公开动物卡与棋盘信息转换成 C++ 可用的数据；随后编写 `engine.cpp` 和 `play.py`。C++ 负责候选规划，Python 负责获取当前观察、读取合法动作、将计划匹配到 SDK 动作并执行。

初版主要设置为：

- 搜索宽度 32：每层保留有限数量的候选方案。
- 动物潜力折扣 0.56：距离完成更远的图案，其未来价值折得更多。
- 联合考虑三个资源的分配，而非独立贪心放置。

中间有命名冲突等编译修复，修完后开始跑完整游戏。这不是一次生成即完成的程序。

## 3. 首局赢了，也暴露了终局处理问题

**日志：`item_18`–`item_24`。**

第一局 GT 结果是 **95:77**。日志同时出现 `PilotError: game_not_active`：游戏已经结束，但驱动又尝试获取活动局面。这个异常不等于首局没完成；GT 已记录自然终局。

Agent 写入 manifest 和启动说明，并成功调用一次检查点接口，得到：

`5e9066a454dfb651fbeb0d319811bcecf88017b1e2a6f9f52adb0aa3f5701093`

随后它备份初版，修复终局处理和计划资源摆放前后的动物动作选择，再用更宽的搜索跑第二局。**终局处理修复发生在这次检查点之后，不能算进已经保存的检查点。**

最终评测时，可信 runner 会在 GT 自然结束后停止控制器；这也解释了为什么含上述终局处理缺陷的早期提交仍能被有效评测。

## 4. 自己搭模拟器，减少对 GT 对局额度的依赖

**日志：`item_25`–`item_35`。**

第二局 **79:68**。Agent 用公开规则编写 `dev/sim.cpp`，让候选参数对抗较早的启发式版本，并启动并行比较。

第一批比较包括：搜索宽度、动物估值权重、动物完成距离折扣、卡槽代价。以下是该批已完成的 24 局模拟结果：

| 变种 | 模拟平均分 | 相对模拟对手平均分差 |
|---|---:|---:|
| 初始参数 `base` | 93.96 | -2.17 |
| 更宽搜索 `wide` | 95.88 | -1.71 |
| 更强动物权重 `high_animal` | 91.50 | -1.50 |
| 更低距离折扣 `low_decay` | 92.96 | +0.96 |
| 更高距离折扣 `high_decay` | 91.08 | -4.58 |

这批结果没有显示“动物权重越大越好”或“搜索越宽越好”。Agent 接下来检查计分，并继续探索距离折扣。

**这些是自建模拟器结果，对手不是冻结 RL；不能与真实 GT 分数直接横比。** 自建模拟不增加 GT 对局名额，但消耗本地 CPU 与墙钟预算。

## 5. 先检查计分，再修改动物估值

**日志：`item_36`–`item_48`、`item_66`。**

它将记录下来的真实棋盘送入自写计分器，与公开观察中的分数比较。日志先记录 214 个棋盘状态的检查，随后扩展为 **434 个棋盘、0 个分数不匹配**。这是记录状态上的一致性检查，不是整个模拟器正确性的完整证明。

接着尝试动物图案/计分轨道相关估值变种，以及更低折扣和更宽搜索。第二批每种 80 局模拟中：

| 变种 | 模拟平均分 | 平均分差 |
|---|---:|---:|
| `base` | 94.59 | +2.25 |
| `track` | 95.01 | +2.74 |
| `wide128` | 94.39 | +1.53 |
| `short128` | 96.78 | +4.55 |

同时，宽度 256 的第三局真实游戏为 **83:70**。前三局使用不同环境，不能凭 95→79→83 的变化判断搜索加宽降低了能力。

## 6. 从“多留候选”转向“向后多看一点”

**日志：`item_49`–`item_78`。**

Agent 加入针对剩余可见资源组合的下一回合前瞻，并修改资源供应、终局处理相关估值。工程上也补了计划失效后的重新选择、规划器失败/超时后的合法动作回退，以及部署计算预算方面的保护。

这一阶段出现的真实成绩包括：

- 宽度 64、折扣 0.43、前瞻候选数 12：**115:71**。
- 相近设置但动物估值变种不同：**82:73**。
- 宽度增加到 128：**90:82**。

在第四批已完成的 80 局模拟中，`short32` 平均 96.51，`short128` 为 94.33，`shortlook` 为 98.31。Agent 的公开进度消息因此转向“前瞻可能比单纯加宽更有用”。这只是当时模拟结果给出的方向，不是正式显著性结论。

## 7. 增加换位实验和终局动物分配

**日志：`item_79`–`item_119`。**

它修改模拟器以支持换位比较，继续扩大候选宽度。第七局使用宽度 256，真实结果为 **103:77**。

随后它加入终局动物分配：多个动物卡可能竞争同一个可放动物的位置，不能简单地把各卡能够得到的收益相加；需要按各卡计分轨道和剩余数量，选择互不冲突的摆放组合。

为检查这段计算，它另写 Python 递归求解程序，测试真实观察得到的局面及构造的竞争位置。实际输出为：

```text
states 664 outputs 664 mismatches 0 []
```

这验证了这批局面上的两个实现一致，不等于新策略已经证明优于旧策略。启用该终局计算的第八局真实结果是 **103:73**。

有些模拟在开发结束前没有完成。例如：

| 实验文件 | 已落盘模拟局数 | 计划局数 |
|---|---:|---:|
| `exp4_tracklook.csv` | 59 | 80 |
| `exp5_wider_shortlook.csv` | 10 | 80 |
| `exp5_deep_shortlook.csv` | 10 | 80 |
| `exp6_exact13_seat0.csv` | 12 | 40 |

因此不能把整批实验当作完成的公平排名，也不能声称终局改进的双座位对照已经跑完。

## 8. 选定工作目录中的默认设置，跑最后两局

**日志：`item_121`–`item_130`。**

Agent 将工作目录中的默认设置改为宽度 64、折扣 0.43、前瞻候选数 12，并启用终局动物分配。它更新说明文件，连续运行最后两局，分别得到 **96:80、89:60**。

十局真实开发过程可以对照如下：

| GT 局次 | 当时的主要设置/变化 | 自己:对手 |
|---|---|---:|
| 1 | 初版，宽度 32；含 SDK 调试；随后保存唯一有效检查点 | 95:77 |
| 2 | 修复驱动、宽度 128 | 79:68 |
| 3 | 宽度 256 | 83:70 |
| 4 | 宽度 64、折扣 0.43、前瞻 12 | 115:71 |
| 5 | 上述设置加另一动物估值变种 | 82:73 |
| 6 | 宽度 128、折扣 0.43、前瞻 12 | 90:82 |
| 7 | 宽度 256、折扣 0.43、前瞻 12 | 103:77 |
| 8 | 宽度 128、增加终局动物分配 | 103:73 |
| 9 | 最后工作目录默认设置：宽度 64、前瞻与终局分配 | 96:80 |
| 10 | 与第 9 局相同默认设置 | 89:60 |

这张表展示迭代顺序，**不是同种子消融曲线**。每局环境不同，且多处代码可能同时修改。

## 9. 最后的工程交付没有赶上预算

**日志：`item_131` 及后续 `turn.failed`。**

Agent 最后启动一个较长的命令，计划依次重新编译、运行验证、汇总实验、写验证报告，然后调用检查点、注册程序并结束开发。

但该命令尚未完成，后续模型请求已经因输入额度不足被拒绝，原生会话退出。账本最终为 **81 次生成、1,982,961 输入 token、70,865 输出 token**；没有第二次成功保存检查点的记录。

所以有两个不同的产物：

| 产物 | 内容 | 是否进入本轮有效评测 |
|---|---|---|
| 已冻结的早期检查点 | 宽度 32、折扣 0.56 的初版搜索与驱动 | 是 |
| 最终工作目录 | 后续前瞻、动物终局分配、可靠性修改及说明 | 否；留作证据，未替它补交 |

这次最明确的工程教训是：**可执行进展应及时保存，不能把检查点、验证报告和清理全部排在预算末尾。** 首局后的早期检查点保住了最终可用提交；后续改进的增益则没有得到有效冻结测试。

## 10. 开发结束后的独立测试，不再反馈给开发者

评测使用上述早期检查点。c3 的 L10/L20/L40 每档均为 8 胜 2 负、均分 97.8；相同种子下三档逐局结果一致，因为程序不调用模型。修复测试运行器的超时结算问题后，c4 用全新种子测试同一程序，10 胜、均分 90.7。

这些结果证明早期程序可用，**不能用来证明后来尚未提交的终局改进更强**。c4 无前期开发对照的均分为 32.5，但随机接管占本方动作的 67.07%，具体解释见[完整结果与成本报告](Results_20261115_zh.md)。

## 与基础设施工作的边界

以上主线是被测 Agent 的行为。此前 c1/c2 的上下文压缩、输入预检配置调整，以及 c3→c4 的超时结算修复，是外部工程工作，不是它自己改进了策略。c3 从空白开始，没有继承 c1/c2 的程序；c4 没有再开发，只评测既有冻结提交。
