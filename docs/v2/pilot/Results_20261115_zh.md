# Harmonies 原生 Agent 开发试跑：2026-11-15

本报告区分开发表现、有效冻结提交、独立测试和基础设施失败。参与者为隔离的原生 Codex 0.167.0 / GPT-6-Astra medium，通过自有 API 路由运行；工程实现会话不作为被测参与者。

## 实验与实际提交

环境为 Known 双人 `side_a_base32_no_spirits_duo`，对手固定为联合策略池中的 `legacy` RL。只开放公共规则、静态组件目录、SDK 和受控 GT 服务；没有环境源码、对手权重、个人历史或测试反馈。GPU 按本轮原方案禁用，没有额外神经策略训练。

开发上限为 10 个 GT 对局、100 次生成、2M 输入/256K 输出、2 小时、8 个物理核、57,600 核秒、32 GiB。测试每局 2 核、120 核秒、8 GiB、1,200 秒墙钟、单决策 120 秒；L10/L20/L40 同时调整调用数与累计 token 上限。输入预检统一采用 131,072 上限，原生自动压缩阈值 32,000。具体配置与校准变更见 [运行说明](README_zh.md)。

c3 参与者自行写出 C++ 回合搜索、Python SDK 驱动和自己的模拟器，并用真实开发轨迹检查计分。真实 GT 开发的 10 局依次为：95:77、79:68、83:70、115:71、82:73、90:82、103:77、103:73、96:80、89:60。它们使用持续变化的参数，不能当作同一策略的测试胜率；自写模拟器中的局数也不能计作真实 GT 局数。

**最终有效提交是早期检查点，不是最后的可变工作目录。** 参与者在输入额度耗尽前未完成最终封装；最后一个封装命令仍在执行，原生 CLI 随后因额度拒绝退出。运行器没有免费补写检查点，也没有依据测试得分挑选程序。

冻结 SHA256：`5e9066a454dfb651fbeb0d319811bcecf88017b1e2a6f9f52adb0aa3f5701093`。该提交为程序入口 `play.py`，使用宽度 32 的三资源回合搜索、精确地形计分和按距离折扣的动物图案潜力（默认折扣 0.56）；不是 RL，也不是每步调用 LLM。后续更宽搜索、第二回合前瞻和终局动物分配改动没有进入这个冻结提交。

c4 的 5 个换位配对种子全部有效，开发后相对无前期开发的平均得分差为 **+58.2**。c3 与 c4 不重复的程序测试合计 20 局为 18 胜，均分 94.25；这是同一提交对同一冻结对手的校准描述，不是独立开发重复。

无前期开发对照仍允许原生工具和局内写程序，并非禁止工具的纯语言模型走棋。10 局的模型额度最终均受输入 token 限制，另出现 12 次单决策超时；修复后全部自然结束，无冻结或未知 usage。随机代走 330 次、Agent 动作 52 次、注册程序动作 32 次、规则强制推进 78 次。表中随机比例以本方全部动作（含强制推进）为分母；只看主动选择动作，随机代走占 79.71%。因此得分差同时反映策略与预算内交付控制器的能力，不能全部归因于纯棋力。原始 `first_binding_limit` 字段只比较模型额度，不代表包括单决策超时在内的所有限制中最先发生的事件。

c3 三档使用同一组 5 个新种子、每个换位两局。三档逐局分数、步数与提交哈希一致；这 30 场执行只有 10 个不重复的种子/座位组合，统计时以 5 个换位种子为单位，不能当作 30 个独立样本。在线 LLM 调用为零，所以本轮没有测出在线模型预算的收益曲线。

c3 无开发对照启动 7 场后因基础设施问题自动停止，另 3 场未启动：单决策超时终止本地控制器时，上游生成未结算；立即续会话触发 in-flight 拒绝，断开的流又可能留下未知 usage。原始记录包含 3 个 `agent_failure` 和 4 个 `infrastructure_failure`，但均受此路径影响，不能作为“无开发胜率为零”的证据。所有原始记录与成本保留。

c4 修复原请求的断流结算和同会话续跑衔接，真实验收通过后，沿用同一冻结提交，在全新且与 c3 不重叠的 5 个种子上进行 L20 开发后/无开发各 10 场配对比较。没有重新开发、继承旧对照文件或回放失败局，总八小时截止不延长。

合计约 **2.67 核小时**，GPU 为 0。已知输入中 5,486,326 为缓存子集，输出中 29,804 为推理子集。c3 受影响对照另保留 7 条未知 usage 请求的额度预留：输入 356,152、输出 28,672；没有将其当作零费用或确认实际费用。c4 全部请求已结算。

最终有效开发一次耗费 81 次生成、1,982,961 输入/70,865 输出、约 34.05 分钟活跃墙钟。之后 c4 程序部署平均 2.30 核秒/局、在线模型调用 0；无前期开发平均 24.57 核秒/局、10.9 次生成、226,818 输入/8,002 输出 token。上述是这次实际消耗，不是未来任务的保证。

所有记录的控制器均确认清理；没有观测到累计 CPU/整局墙钟/RSS 超额（单决策超时另记）。实际最大采样缺口 4.92 秒、最大清理延迟 1.45 秒、采样峰值 RSS 0.83 GiB，不能用目标 50 毫秒采样间隔或零观测超额冒充内核硬限制。

缓存输入是输入 token 的子集，推理输出是输出 token 的子集，均不重复累计。未结算/未知请求的预留单列，不代表确认账单或严格计费上界。统计包含各配置试跑和验收，但不包含工程实现会话的模型使用、宿主机安装/pytest CPU、可信 GT/对手服务 CPU；不能称为整个项目的总成本。并行阶段墙钟相加不等于实验历时。

真实运行在 AMD EPYC 7H12 主机，测试四路分别绑定 0–1、2–3、4–5、6–7，使用不同物理核；开发使用 8 核，GPU 为零。c3 的开发计算约 8,936 核秒，部署每局约 2.2 核秒。对这份冻结程序，120 核秒有很大余量；不应因此推断别的策略或模型也只需要这些资源。

程序测试的端到端墙钟明显大于被测进程 CPU 时间，部署吞吐不能只按搜索耗时估算。共享文件系统上的持久账本、服务请求和监测都有成本；当前数据尚未将这些开销完全拆分。后续可单独检查通信与持久化，不能在本轮中途改变计量口径来美化吞吐。
