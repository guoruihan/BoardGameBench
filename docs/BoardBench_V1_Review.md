## 3. 两个确定可复现的代码问题

### 3.1 合并额外训练结果时，必须检查与主验证／测试集的交叉污染

优先修复。位置：`src/boardbench/benchmark.py` 的 `validate()`，当前第 84–89 行。

`training.train()` 会检查每个 run 自己的 train／validation／test 是否互斥，但 `validate(..., extra_training=...)` 只读取主 run 的划分，然后直接加入另一个 run 的候选。因此，两个分别合法的 run，合并后可能使用训练过主验证或测试种子的模型。

已用小型 Micro 训练实际复现：

| 划分 | 主 run | extra run |
| --- | --- | --- |
| train | 100–103 | 200–205 |
| validation | 200 | 400 |
| test | 201 | 500 |

两个 run 都能独立训练成功。合并验证没有报错，受污染的 `rl_trained_000003` 还被选中；selection 继续记录 `test_used=false`。这个标记仅说明没有直接用测试成绩选模型，不能证明模型没有训练过测试局。

最小修复要求：

1. 在评估候选前，读取所有来源 run 的 task、规则版本和 splits。
2. 拒绝任意来源训练集与本次主 validation／test 的交集，同时保持主 validation 与 test 互斥。
3. 每个候选保存自己的来源 run、训练配置和划分。候选标识应能区分不同 run；目前仅按 checkpoint 文件名去重，会静默丢弃不同 run 的同名阶段。
4. 增加两种回归测试：上述交叉污染必须拒绝；相同任务且划分合法的多个 run 可以正常参与验证。

这属于实验正确性检查，不需要引入额外服务或复杂隔离机制。**当前交付的实际 A/B 划分已另行核对，没有发现泄露。**

### 3.2 网络宽度配置没有传入验证／导出

位置：`src/boardbench/training.py` 的 `train()` 当前第 42 行；`src/boardbench/benchmark.py` 的 `candidates()`／`build_solver()` 当前第 55–68 行。

训练支持 `config.hidden`，候选生成却没有携带它。加载候选时默认使用 128，而权重加载又严格检查架构。

实际复现：将 Micro 配置设为 `hidden=32`，两局最小训练成功且参数更新；随后生成候选并加载，报错：

```text
policy artifact mismatch: hidden
```

最小修复要求：从对应权重 metadata 或来源训练配置构建网络，不要在验证阶段自行假设宽度。保留已有架构一致性检查。用非 128 宽度跑通训练 → 验证 → 导出 → 新进程推理，并覆盖 extra run 使用另一宽度的情况。

当前交付全部使用 128，因此这批结果仍可复现。

## 4. 策略结果应该怎样理解

以下为同一组 128 个测试种子上的均分，从提交的逐局记录重新计算。

| 游戏 | 随机 | 启发式 | 搜索 | 已训练 PPO | 未训练 PPO |
| --- | ---: | ---: | ---: | ---: | ---: |
| Micro Tiles | 5.70 | 14.84 | 15.05 | 5.84 | 5.77 |
| Take It Easy! | 7.61 | 135.84 | 139.45 | 10.55 | 7.72 |
| Harmonies | 22.93 | 44.30 | 62.58 | 55.23 | 21.02 |

**Micro：目前主要验证了训练链路可以运行，没有建立有效学习基线。** 最简单的任务上 PPO 仍接近未训练网络，应先诊断数据、表示、优化与推理方式，不能仅凭参数更新判定“已经学会”。

**Take It Easy!：人工启发式显著更强，PPO 尚未展示可靠收益。** 这不说明任务不适合学习，只说明当前流程和预算没有建立足够强的学习基线。

**Harmonies：存在清晰的参数学习收益，是本次最有价值的结果。** 已训练 PPO 超过启发式，但仍低于当前搜索。还应限制结论范围：

| Harmonies 得分拆分 | 地形分 | 动物分 | 总分 |
| --- | ---: | ---: | ---: |
| 启发式 | 36.84 | 7.46 | 44.30 |
| 搜索 | 48.81 | 13.77 | 62.58 |
| 已训练 PPO | 48.44 | 6.79 | 55.23 |

PPO 相对启发式的优势主要来自地形，而非更强的动物牌协同。后续应同时报告动物分、动物放置次数、完成卡数等，避免总分掩盖策略覆盖不足。

同一测试 seed 上，已训练减未训练的配对差及近似 95% 区间为：

| 游戏 | 均值差 | 近似 95% 区间 |
| --- | ---: | --- |
| Micro Tiles | +0.08 | [-0.81, 0.97] |
| Take It Easy! | +2.84 | [-0.74, 6.42] |
| Harmonies | +34.20 | [32.01, 36.40] |

区间按 128 个配对差的均值 ± 1.96 × 标准误计算，只描述这份训练产物在不同环境种子上的不确定性。当前只有一个训练随机种子，A/B 是同种子下不同预算的实验，不能把它们当成独立训练重复。

## 5. 当前搜索与效率结论的边界

`src/boardbench/solvers/board.py` 当前第 128–153 行的搜索：只考察启发式排名前 4 个动作，每个动作 2 次 rollout，深度 3 个原子动作，每次决策最多 24 个模拟步。

对 Harmonies 而言，3 个原子动作可能连一个完整回合都覆盖不了。这个方法可以作为明确预算下的搜索基线，但不能代表强规划上限，也还不能据此判断任务难度已经充分挖掘。

提交记录中的 Harmonies 平均每局耗时为：

| 方法 | 纯 solver 决策时间合计 | Runner 每局 wall time |
| --- | ---: | ---: |
| 启发式 | 0.0447 秒 | 0.1441 秒 |
| 搜索 | 1.3557 秒 | 1.4602 秒 |
| 已训练 PPO | 0.0321 秒 | 0.1461 秒 |

因此，可以说 PPO 在这次实验里以接近启发式的每局运行时间取得更高分，且相对搜索明显更快、分数稍低。不能把纯模型推理的优势直接写成相对启发式的整体加速。Runner 每局时间也不等于包含模型冷启动、前期训练和浏览器展示的全部使用成本。

这组结果已经值得继续，但目前仍是人工设计策略的性能与成本比较，尚未检验 V2 所要求的“agent 自主建立、训练和使用系统”。V1 暂不包含自主 agent 是符合范围约定的。

## 6. 规则与网页的验收意见

三环境正常玩法没有发现阻断问题。Harmonies 的回合内拿牌／放资源／放动物穿插、每回合取牌次数、完成卡释放槽位、延迟补牌、动物进度保留、地形计分、单人弃置与终局处理，均与交接规范一致。

资源不足以补满市场时结束，是本项目已经约定的末袋裁定；不应在修复时误当成新发现的官方规则错误。

网页通过本地 Python 服务调用同一套规则引擎，提示、接管、存取和同 seed 挑战均有真实实现。桌面和手机截图布局清楚。

需要补一项定向浏览器验收：`scripts/browser_v1_check.py` 当前第 82–84 行总选 `legal_actions[0]`；现有 Harmonies 手动整局及 RL 示例都没有实际放动物。这意味着已有截图和浏览器测试尚未覆盖关键卡牌操作，**不意味着已经证明按钮有 bug**。

补一个固定局面或确定动作序列，实际点选并断言：

1. 在两次资源放置之间拿牌。
2. 选择动物卡与合法落点，成功放置动物。
3. 放完最后一只动物后卡片完成、槽位释放；若本回合尚未取牌，可以继续合法取牌。
4. 保存恢复后卡片进度、棋盘动物与待放资源一致。

手机端堆叠详情目前主要通过 hover title 查看，可以增加点击格子展示层级详情；这是易用性改进，不作为当前阻塞项。

## 7. 建议交给本地 agent 的下一轮任务：V1.1

保持当前架构和三个环境，集中完成以下工作，不增加新游戏或自主 agent 框架。

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 修复候选架构传递、extra run 划分与来源记录 | 非默认宽度完整流水线通过；交叉污染被拒绝；不同 run 不因同名 checkpoint 静默丢失 |
| 2 | 诊断 Micro 学习失败 | 先在很小的固定训练集合上检查能否学到有效策略，再验证新局；保留失败诊断和曲线，不以“权重变化”代替性能证据 |
| 3 | 加强人工学习与搜索基线 | 总计保持 3–5 类方法即可；在固定并记录的预算下，改善 TIE 学习和 Harmonies 规划，允许结果诚实地不达预期 |
| 4 | 增加训练重复与得分拆分 | 建议至少 3 个独立训练种子；同代码不同权重阶段比较；Harmonies 同时报告地形、动物和完成卡指标 |
| 5 | 补动物牌浏览器场景 | 实际浏览器点选链路与保存恢复断言通过 |

Micro 诊断时可以分别检查训练采样策略与评估 argmax 的得分、状态与动作编码、奖励尺度及优化曲线；这些是待验证的原因，不是本轮已确认的 PPO 算法 bug。本轮静态审查未发现 PPO clip objective、行为 log-prob 或 score-delta 目标中的明显错误。

Harmonies 下一版搜索应至少明确“深度”使用原子动作还是完整回合，并在固定模拟步或时间预算下比较；无需预先指定必须使用某种大型搜索框架。当前分数低也不直接证明必须增加模型大小。

这轮测试结果已经公开用于诊断。下一轮保留原测试集作回归参考，预先固定新的最终测试集合，仍只用训练／验证信息选择配置；不反复根据最终测试排名调参。

V1.1 的目标是建立可信的人工学习与规划参照，确认任务的提升空间和成本关系。无需为了宣称 SOTA 无限制增加预算；如果某个任务仍学不动，应交付可定位的实验结论，而不是继续堆积工程。
